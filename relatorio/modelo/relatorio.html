Sumário

1 Introdução

Este relatório documenta a atividade prática da disciplina IAL-215 – Banco de Dados NoSQL, que pede uma aplicação CRUD com os dados persistidos obrigatoriamente em MongoDB. O grupo escolheu como tema o Caderno de Campo: um sistema para registrar os talhões de uma propriedade rural, as operações feitas em cada um (preparo de solo, plantio, adubação, pulverização e colheita) e o estoque de insumos. Os dados de exemplo são de uma propriedade fictícia, o Sítio Santa Luzia, em Pompeia – SP.

O problema que o sistema resolve é conhecido no campo: o registro costuma ficar em caderno de papel ou em planilhas soltas, e fica difícil saber o que foi aplicado em cada talhão, quanto ainda resta de cada insumo e quanto custou a safra. Reunir esses registros em um só lugar permite responder essas perguntas com consultas e agregações, o que combina com o curso de Big Data no Agronegócio.

O MongoDB foi escolhido porque o dado do tema tem forma de documento. As operações de um talhão são sempre lidas junto com ele, então cabem como um array dentro do próprio documento, sem junções. Os operadores de array ($push, $pull, arrayFilters) e o aggregation framework cobrem as consultas de análise, e o validador $jsonSchema mantém a disciplina dos dados mesmo sem esquema fixo.

3.3 Decisões de modelagem

Operações embutidas. Uma operação só existe dentro de um talhão e é sempre consultada junto com ele (a ficha mostra o talhão e o histórico). Embutir evita uma coleção a mais e uma junção a cada leitura, e permite alterar a operação e o talhão no mesmo documento. É a escolha indicada para relações “contém” em que o array tem tamanho limitado, como acontece em um talhão ao longo de uma safra.

Insumo referenciado, com cópia. O insumo fica em coleção própria porque tem estoque e é compartilhado por vários talhões; embutir geraria cópias do estoque. Dentro de cada operação, porém, vai uma cópia dos campos que não podem mudar com o tempo (_id, nome, unidade e preco_unitario do dia). Assim o custo de uma adubação feita em março não muda se o preço do insumo mudar em maio, e o _id guardado permite o $lookup quando é preciso buscar dados atuais.

8 Como executar

Requisitos: Node.js 22 e Docker. A aplicação abre em http://localhost:3415 e o mongo-express em http://localhost:8089.

git clone {{GITHUB}}.git
cd caderno-de-campo-mongodb
cp .env.example .env
npm install
npm run db:up      # sobe o MongoDB (27029) e o mongo-express (8089)
npm run db:seed    # cria coleções, validadores, índices e os dados de exemplo
npm start          # aplicação em http://localhost:3415
npm test           # testes automatizados (banco caderno_de_campo_teste)

Para usar o MongoDB Atlas no lugar do contêiner, basta trocar a URI de conexão no arquivo .env. A demonstração de comandos pode ser executada com mongosh "mongodb://127.0.0.1:27029/caderno_de_campo" docs/comandos-mongosh.js.

10 Considerações finais

A aplicação cumpre o que a atividade pede: CRUD completo sobre duas coleções, com os dados persistidos em MongoDB e os principais recursos do banco aparecendo no código e nos comandos (validação por $jsonSchema, índices único e de texto, operadores de array, busca textual e agregações). A modelagem com operações embutidas deixou a ficha do talhão simples de ler e de alterar.

Algumas limitações ficam registradas. O aplicativo não usa transação. Ao registrar uma operação, o estoque é baixado com um updateOne condicional (só atualiza se estoque for maior ou igual à quantidade) e, se o passo seguinte falhar, a baixa é desfeita na mão. Isso funciona para o uso da aula, mas não dá a garantia de uma transação. A aplicação também não tem autenticação, pois foi pensada para uso local. Como melhorias, o grupo aponta o uso de transações em um cluster com réplicas, o controle de usuários e a importação de dados de máquinas e sensores, que combinaria com a área de Big Data.
